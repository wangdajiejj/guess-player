# 第 5 步 · 部署步骤 & 微信审核注意事项

> 主体：**个人** | 类目：**工具类 → 效率** | 技术：小程序原生 + 云开发
> 预计总耗时：**注册 1 天 + 备案 1~20 个工作日 + 开发部署 1 天 + 审核 1~7 天**

---

## 1. 上线时间线（顺序不能乱）

```
① 注册小程序（个人主体，身份证 + 人脸核验）        ~30 分钟
② 填写类目：工具类 → 效率                          ~5 分钟
③ 小程序备案（ICP 备案，强制，未备案无法上架）     1~20 个工作日  ← 最长的一环，尽早发起
④ 开通云开发、建集合、导数据、传云函数             ~2 小时
⑤ 开发者工具真机调试                               ~半天
⑥ 提交审核                                        1~7 天
⑦ 发布
```

> **备案可以在开发期间并行做**。备案需要填服务内容标识、类目，和小程序的实际内容要对得上，
> 所以建议先把类目定死（工具→效率）再发起备案，避免改类目后重新备案。

## 3. 云开发环境

### 3.1 开通

微信开发者工具 → 工具栏「云开发」→ 开通 → 新建环境（**个人实名后可免费开 1 个环境**）。
记下环境 ID，形如 `guess-player-1a2b3c4d`。

### 3.2 两个必改开关

**改点 1 · 环境 ID**（`miniprogram/app.js` 的 `ENV_ID` 常量）：

```js
const ENV_ID = 'guess-player-1a2b3c4d';   // ← 换成你自己的
```

云函数里用的是 `cloud.DYNAMIC_CURRENT_ENV`，不用改。

**改点 2 · 切回正式版**（`app.js` 顶部的 `USE_MOCK` 必须是 `false`）

**别手改，双击这个脚本**：

```
scripts\关闭本地测试-提审前必点.bat
```

它会拆掉全部 MOCK 段、删掉 6 个 `mock-*.js` 与 3 个 mock 脚本（省约 130 KB 主包），
再跑一遍 `check-mp.js` —— 看到 **15 条全绿**才算干净。

开着 `USE_MOCK` 上传意味着：**比对逻辑和 548 人的答案被打进了客户端**，
别人反编译后遍历候选池就能试出每天的答案 —— 这是全项目的架构红线（见 docs/03-algorithm.md §6）。

`check-mp.js` 第 7 组的 4 条断言会守着这件事，任何一条不满足就直接失败：

```
✓ app.js 里能找到 USE_MOCK
✓ Mock 已关闭（正式包状态）
✓ miniprogram/utils 下没有残留的 mock-*.js
✓ 没有页面/组件还在 require mock-*
```

> 开发期想再本地看效果，双击 `scripts\开启本地测试.bat` 即可切回去。
> 两个方向来回切**逐字节可逆**（已实测 3 轮 SHA-256 比对）；
> 机制与存档说明见 `_mock-backup/还原说明.md`。
> ⚠️ 本地测试模式下面试/演示可以，**上传提审绝对不行**。

### 3.3 建集合与索引

云开发控制台 → 数据库 → 新建集合 `players` / `games` / `meta`。
（`user_stats` 不需要——个人主体禁 UGC，排行榜已砍，战绩只存本地。）

| 集合 | 索引名 | 字段 | 唯一 |
| --- | --- | --- | --- |
| players | `idx_id` | `id` 升序 | ✅ |
| players | `idx_pool` | `active` 升序 + `fame_level` 升序 | ❌ |
| players | `idx_position_group` | `position_group` 升序 | ❌ |
| games | `idx_gameid` | `gameId` 升序 | ✅ |
| games | **`idx_unique`** | **`uniqueKey` 升序** | ✅ **必须唯一，幂等开局的兜底** |
| games | `idx_openid_datekey` | `_openid` + `mode` + `dateKey` 升序 | ❌ |

> ⚠️ 唯一索引必须是 `uniqueKey`，**不能**用 `_openid + mode + dateKey`。
> 后者会把 endless 模式也约束住，导致"一天只能开一局无限模式"。
> （这个坑是 `scripts/test-flow.js` 的并发用例抓出来的，见 docs/04-testing.md §5。）

### 3.4 设置权限（重要）

每个集合 → 权限设置 → **自定义安全规则**：

`players` —— 所有人可读，仅管理端可写：

```json
{ "read": true, "write": false }
```

`games` —— **双私密**（客户端完全不可读写，所有操作走云函数）：

```json
{ "read": false, "write": false }
```

`meta` —— 同 players：

```json
{ "read": true, "write": false }
```

> 即便设为 `false`，也不能替代"云函数不下发 answerId"——真正的防线是 `util.publicGame()` 的字段白名单
> 和 `gameResult` 的 `status === 'playing'` 守卫。权限只是第一层。

### 3.5 导入球员数据

正式题库是 `database/players.full.jsonl`（**500 条**）。想先跑通全流程可只导
`players.sample.jsonl`（10 条），确认链路通了再导全量：

```bash
python database/validate.py database/players.full.jsonl 2026-10-11 --fix  # 必须 0 阻断级错误
```

控制台 → 集合 `players` → 导入 → 选 JSON Lines 文件 → **冲突处理：upsert**（`_id` 用 `p001` 这种字面量，
重导不会重复插入）。

> ⚠️ **导入后必须核对集合条数 = 548**。微信导入界面偶发静默丢条；一旦少了，
> 客户端候选池不全，答案又可能落在缺失的那部分 —— 直接变成死题。
> 核对方式：集合页看总数，再在小程序里搜一个排在最末的球员（如 `p500`）确认能搜到。

> 微信的导入只接受 `.json` / `.csv`。jsonl 是每行一个 JSON，需先转成数组格式：
> ```bash
> python -c "import json,sys;print(json.dumps([json.loads(l) for l in open('database/players.full.jsonl',encoding='utf-8') if l.strip()],ensure_ascii=False))" > players.json
> ```
> 然后导入 `players.json`，文件格式选 JSON，冲突处理 upsert。

### 3.6 写入 meta

`meta` 集合手动加 3 条，`_id` 必须一字不差：

```json
{ "_id": "daily_salt",  "salt": "换成一串你自己的随机字符串", "mode": "per_user" }
{ "_id": "answer_pool", "minFameDaily": 4, "minFameEndless": 3, "activeOnly": false, "excludedIds": [] }
{ "_id": "players_meta","playerVersion": "2026-10-25", "playerCount": 548, "updatedAt": 1791676800000 }
```

- `mode: "per_user"` = 每人每天题目不同（当前采用）；
  改成 `"global"` 则全网同题，**改完记得同步改前端分享文案**。
- `minFameDaily`(4) 比 `minFameEndless`(3) 高一档：**每日一题只用大家都认识的球员**，
  冷门球员只能被猜、不能当每日答案 —— 没听说过的人靠推理也唤不出那个人名，只剩挫败。
  自由练习是玩家主动选的，愿意挑战冷门就让他挑战。两个数都能线上改，不用发版。
- 自由练习 2026-10-25 起分三档难度（首页可选）：`star`（明星局，默认 fame=5）、
  `normal`（标准局，默认 fame=4）、`all`（全员局，走 `minFameEndless`）。
  需要线上调档时在 answer_pool 里加 `"minFameStar": 5, "minFameNormal": 4` 即可。
- 老字段 `minFame` 仍作兜底（两个新字段都没配时读它），方便灰度回退。
- `playerVersion` 每次改球员数据都要 +1，否则客户端不会重新拉取候选池。

## 7. ⚠️ 审核注意事项（重点）

### 7.1 为什么不能选"游戏"类目

**「微信小程序」和「微信小游戏」是两套独立账号体系**：

- 小程序原生（WXML）的「游戏」类目**不向个人主体开放**，选了必拒；
- 小游戏（Canvas/Cocos/Unity）个人主体可选「休闲益智」，纯广告变现免版号，
  但要多交**软件著作权（约 60 天）**、自审报告、且 UI 得用 Canvas 重写。

本项目是 WXML 原生，所以走**工具类 → 效率**是唯一顺畅的路。代价：
**不能用"游戏化"的核心卖点去做推广文案**（见 §7.2）。

### 7.2 文案红线（改这几处就能避开 80% 的驳回）

| 位置 | ❌ 不要写 | ✅ 改成 |
| --- | --- | --- |
| 名称 / 简介 / 关键词 | 游戏、竞技、闯关、挑战赛、答题赢奖 | 工具、查询、资料、知识、识图 |
| 结果页分享文案 | ~~今日已通关~~（代码里已改掉） | 今日已答对 |
| 模式名 | ~~每日挑战 / 无限模式~~（代码里已改掉） | **每日一题 / 自由练习** |
| 首页 | ~~第 3 关~~ | 今日第 1 题 |
| 任何位置 | 排行榜、好友、PK、段位、积分商城 | —— 全部不要有 |
| 分享图 | 分数、排名、连续签到 | 只留色块和"用了 X 次" |

**代码里已经处理过的**：`pages/result/result.js` 的 `onShareTimeline` 已从"通关"改为"答对"。
建议再自查：`index.wxml` / `help.wxml` 里不要出现"挑战成功""闯关"字样。

### 7.3 球员形象：程序绘制（已不涉及 AI 生成内容）

原方案是 AI 生成 200 张球员像，**2026-10-11 改为纯代码绘制**：按球队配色做渐变底
+ 斜纹 + 姓氏首字 + 位置徽章，**全包零位图**（见 `docs/01-PRD.md §7.1`）。

这带来两个直接好处，提审时可以主动说明：

- 《人工智能生成合成内容标识办法》(2025-09-01) 的显式/隐式标识义务**不再适用** ——
  包里没有任何 AI 生成内容，也没有任何图片文件；
- 不存在"AI 生成的可识别真人形象"这一档争议，肖像权风险从根上消失。

提审时建议在「补充说明」里主动写明：

> 本小程序不使用任何真实球员照片、AI 人像或第三方版权图片。
> 球员形象由代码按球队配色现场绘制（色块 + 姓氏首字 + 位置徽章），
> 不含俱乐部徽章、赞助商标识与真实球衣号码，不涉及肖像权、商标权与赛事版权。

### 7.4 肖像权与商标（最容易被投诉的点）

| 风险 | 规避做法 |
| --- | --- |
| 球员肖像 | 不用任何真人照片或 AI 人像，只画抽象色块 + 姓氏首字 → 不构成"可识别的外部形象" |
| 俱乐部徽章 / 赞助商 Logo | 绘制时不含任何徽章/Logo 元素（`player-badge` 只取队色） |
| 真实球衣号码 | 不在头像上体现。号码还是游戏线索，图上出现等于剧透 |
| 球员姓名 / 俱乐部名 | 属于事实性信息，正常使用没问题 |
| 被投诉后的通道 | 设置页保留「意见反馈」入口，并在结果页写明"如认为不妥可反馈删除" |

### 7.5 隐私（个人主体的高频驳回原因）

- **必须在 mp 后台 → 设置 → 服务内容声明 → 用户隐私保护指引**：勾选「不采集」或逐项声明。
  **没填这个，提审直接被拒**，这是个人主体最常见的驳回原因。
- 代码侧已经做到：无登录、无手机号、无位置、无通讯录、无相册读取（保存图片走 `saveImageToPhotosAlbum`，
  是微信托管的一次性授权，不算采集）。
- `app.json` 里保持 `"permission": {}` 和 `"requiredPrivateInfos": []` 为空——**不要手贱加东西**。

### 7.6 其他常见驳回

| 驳回理由 | 整改 |
| --- | --- |
| "服务类目与实际内容不符" | 检查有没有排行榜/分享得积分等；把文案里的"游戏"全删掉 |
| "小程序无法正常使用 / 页面空白" | 提供**测试账号**——本项目无登录，备注里写明"无需账号，打开即用" |
| "存在诱导分享" | 不要写"分享后才能看答案""邀请 X 人解锁" |
| "名称含敏感词/侵犯他人权益" | 别用俱乐部名或球员名做小程序名 |
| "缺少 ICP 备案" | 先去备案，通过了再提审 |

## 8. 上线后运维

| 事项 | 频率 | 怎么做 |
| --- | --- | --- |
| 校准球员数据（转会、号码、年龄） | 每月 | 改 jsonl → `validate.py` → 重新导入 → **`playerVersion` +1** |
| 扩充题库 | 已完成：200 → 500 → **548 人**（2026-10-25 又扩 48 人：现役 12 + 退役传奇 36） | 同上；注意退役传奇必须填真实代表队（否则互绿送答案）。扩池后**必须重跑** `simulate.js` 复核难度，并检查 `MAX_POOL_SIZE` ≥ 新总人数 |
| 看云开发用量 | 每周 | 控制台 → 用量监控，读次数接近 5 万/日时考虑给 `getPlayers` 加 CDN |
| 看崩溃与云函数报错 | 每天 | 控制台 → 云函数日志，搜 `[gameStart]` 之类的前缀 |
| 换每日答案种子 | 半年一次 | 改 `meta/daily_salt`，不影响进行中的对局 |
| 切换"全网同题" | 可选 | `meta/daily_salt.mode` 改成 `global`，并同步改前端分享文案 |

**应急预案**：
- 题库被误清空 → `getPlayers` 返回空 → 前端会提示"题库维护中"，不会崩；
- 某个球员数据明显错误（比如转会没更新）→ 直接改库 + `playerVersion` +1，用户下次启动自动拉新版；
- 收到肖像投诉 → 3 天内下架该球员：把 `fame_level` 改成 1（退出答案池），并在下次版本从候选中移除。
