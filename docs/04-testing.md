# 第 5 步 · 测试方案

> 三层测试，从内到外：**单测（纯函数）→ 流程测试（真实云函数 + 内存数据库）→ 手工用例（真机/模拟器）**。
> 前两层 `cd guess-player && node scripts/xxx.js` 就能跑，不需要真云环境；第三层在开发者工具和真机上做。

## 1. 第 1 层：算法单测（`scripts/test-compare.js`，32 条）

覆盖 `cloudfunctions/_shared/compare.js` 与 `util.js` 的纯函数。

| 分组 | 用例 |
| --- | --- |
| 位置判定 | 细分相同→绿；同类不同细分→黄（中锋 vs 影锋、中前卫 vs 后腰）；跨类→灰（门将 vs 中锋） |
| 国籍 / 联赛 | 相同→绿；不同→灰（**联赛没有"黄色"**，避免"英超和西甲差不多"的歧义） |
| 俱乐部 | 同城不同队→灰；同队→绿 |
| 年龄 | 相同→绿 + `=`；差 ≤2→黄 + 箭头；差 >2→灰 + 箭头；**跨生日当天算周岁** |
| 身高 / 号码 | 同上，公差分别 3cm / 3 号 |
| 惯用脚 | 左右互判灰；**"双脚"是独立取值**，只有双方都双脚才绿 |
| 缺失值 | `height_cm = 0` 按缺失处理，判灰且不出箭头 |
| 时区 | UTC 23:30 必须归属北京时间次日（否则每日挑战会在跨零点时错乱） |
| 字段裁剪 | `publicGame()` 绝不含 `answerId`；剩余次数算法正确 |
| 散列分布 | 20 个不同 openid 同一天的答案必须高度离散（**这条抓出过真实 bug，见 §5**） |

## 2. 第 2 层：流程测试（`scripts/test-flow.js`，77 条）

原理：用 `Module._resolveFilename` 把 `require('wx-server-sdk')` 重定向到 `scripts/mock-cloud.js`
（一个内存版数据库），于是**5 个云函数的 index.js 原封不动地跑起来**，跑完整的"开局→猜测→终局→揭晓"。

```bash
node scripts/test-flow.js
```

mock 实现了被测代码用到的全部 API：`where / orderBy / skip / limit / get / add / doc().get / doc().update / command.gte / runTransaction`，
并且**模拟了 `games.uniqueKey` 的唯一索引**，所以能真正触发并发冲突分支。

| 分组 | 关键断言 |
| --- | --- |
| 开局与幂等 | 重复开局 gameId 不变、不消耗次数、**数据库未新增对局** |
| 并发开局 | `Promise.all` 两次开局 → gameId 一致、只建了一局 |
| 答案分布 | 40 个用户同一天 ≥8 种答案；同一用户 20 天 ≥5 种；`global` 模式下所有人同答案 |
| 猜测判定 | 回合数/已用/剩余递增；verdict 含全部 8 字段且取值合法；重复猜测 1005 且不扣次数；重放结果与实时判定逐字节一致；猜中全绿 |
| 得分 | 第 4 次猜中 = 500 分；失败 = 0 分 |
| 揭晓答案 | 答案 id/姓名正确、含简介三件套、年龄已算好、回放 4 行且每行带球员信息 |
| **答案防泄露** | 未终局揭晓 → 1004 且不带任何数据；扫描全部响应断言无 `answerId`、无答案 id、**无答案姓名** |
| 越权 | 他人猜测/揭晓/续局 → 1003 |
| 无限模式 | 两次开局 gameId 不同 |
| 错误码 | 1001 / 1002 / 1004 / 1005 / 1006 全覆盖 |
| 候选池下发 | 含 `primary_color`/`secondary_color`（画头像要用）；不含 photo_url/intro/fun_fact/meme/search_index/answerId；版本号一致时 `fresh=false` 不重复传输 |

> **写新用例时注意**：`SNAPSHOTS` 是共享数组，做"泄露扫描"类断言前必须 `useBucket(局部数组)`，
> 否则别人猜中的球员 id 会被算到你这个用例头上（这个坑我在第一版里踩过）。

## 4. 性能验收

| 指标 | 目标 | 怎么测 |
| --- | --- | --- |
| 冷启动到首页可交互 | < 2.5s | 开发者工具 → 体验评分 |
| 云函数 `gameStart` | P95 < 400ms | 云开发控制台 → 云函数日志里的"运行时间" |
| 云函数 `gameGuess` | P95 < 500ms | 同上（含事务，会比读慢） |
| 候选池包体 | < 250 KB | **500 条实测 169.7 KB**（gzip 37.7 KB），单条均值 348 B —— 见 `scripts/test-flow.js` 的"候选包字段数受控"。旧预算 120 KB 是按 200 人定的，题库扩容后随之放宽；真瓶颈是主包 2MB 和存储 10MB，170 KB 离两者都很远 |
| 单张球员图 | ≤ 50 KB WebP | `identify -format "%b" *.webp` |
| 首屏请求数 | ≤ 3 | 真机 → 微信开发者工具 Network 面板 |

> 云开发免费额度参考：数据库读 5 万次/日、写 3 万次/日、存储 5 GB、CDN 5 GB/月。
> 一局游戏大约消耗 **1 次写 + 9 次读**，按日活 1000 人每天 3 局算，约 3 万读/3 千写，**够用**。
> 真正的风险是 `getPlayers` 的 500 条读取（**5 页 × 100**，云数据库单次 `get` 上限 100）——
> 靠版本号缓存压到每人只下一次（题库不更新就不重复读）。
> ⚠️ 分页循环**不能写死页数**：曾经是 `page < 3`（硬顶 300），题库扩到 500 后被静默截断，
> 答案落在候选池外会导致游戏无解。现在改成"取不满一页即止"，由
> `test-flow.js` 的「下发条数正确」守着（期望值直接取题库实际条数）。

## 4.4.1 题库体检（`scripts/audit-data.py`）

```bash
python scripts/audit-data.py                 # 基准日取 jsonl 里的 data_as_of
python scripts/audit-data.py 2026-10-11      # 指定基准日算年龄
python scripts/audit-data.py --top=20        # 分布榜显示前 20
```

不进 `一键测试.bat` —— 因为它的产出是**待人工核对清单**，不是能自动判对错的断言。
（`validate.py` 才是阻断式的那个。）两者分工：

| | `validate.py` | `audit-data.py` |
| --- | --- | --- |
| 管什么 | 字段合不合法（译名 / 位置枚举 / `search_index` / 必填项） | 数据好不好用（分布失衡 / 跨记录冲突 / 逻辑死题） |
| 不合格时 | **阻断**，不许导入 | 只报告；退出码只看「有没有死题」 |
| 什么时候跑 | **每次改数据后** | **每次扩题库后**，以及每月校准时 |

**为什么需要第二个**：字段全合法 ≠ 游戏可玩。典型例子 ——
两个球员在 8 条线索上取值完全相同，`validate.py` 一条都抓不到（每个字段都合法），
但玩家无论怎么猜得到的反馈都一样，**永远区分不开他们**。这是逻辑层面的死题，
只能靠跨记录比对发现，也是本脚本唯一会让你退出码变 1 的检查。

其余检查项：

| 编号 | 检查 | 性质 |
| --- | --- | --- |
| 3.1 | 8 项线索完全相同的球员组 | ❌ 阻断（逻辑死题） |
| 3.2 | **现役**球员同队同号 | ⚠ 待核（跨时代重号正常，同年代重号是转会没跟上） |
| 3.3 | 现役年龄 <16 或 >45 | ⚠ 待核 |
| 3.4 | 身高超出 160~215cm | ⚠ 待核（`validate.py` 只警告，这里汇总出来一起看） |
| 3.5 | 同队同位置 ≥ 4 人 | · 区分度预警，非错误 |
| 3.6 | 高漂移联赛（土超/沙特联/美职联/巴甲/阿甲/日职联/韩K联）的现役球员 | · 校准优先看这里 |
| 3.7 | 退役球员周岁 ≥ 85（如梅阿查 116 岁） | · 产品取舍，需拍板 |

## 4.5 可玩性模拟（`scripts/simulate.js`）

单元测试能证明"没写错"，但证明不了"好不好玩"。这个脚本回答一个产品问题：
**8 次机会到底够不够？**

```bash
node scripts/simulate.js              # 每日一题池（fame>=4，250 人）
node scripts/simulate.js --pool=all   # 自由练习池（fame>=3，500 人）
node scripts/simulate.js --quick      # 只跑 40 人，快
node scripts/simulate.js --max=6      # 试算"只给 6 次机会"会怎样
```

两种玩家模型：

| 模型 | 行为 | 代表 |
| --- | --- | --- |
| `random` | 在候选池里随机点，但会按反馈完美过滤 | 难度下界 |
| `greedy` | 每步挑"最坏情况下剩余候选最少"的（minimax 采样 30 个探针） | 老手最优 |

**2026-10-11 实测（500 人题库）**

| 池 | 新手平均（随机+过滤） | 老手平均（minimax） | 老手最坏 | 8 步通关率 |
| --- | --- | --- | --- | --- |
| 每日一题 250 人 | 2.58 步 | **2.37 步** | 3 步 | 100% |
| 自由练习 500 人 | 2.70 步 | **2.49 步** | 4 步 | 100% |

<details>
<summary>对比：扩容前（200 人题库）的基线</summary>

| 池 | 老手平均 | 老手最坏 |
| --- | --- | --- |
| 每日一题 138 人 | 2.21 步 | 3 步 |
| 自由练习 200 人 | 2.33 步 | 4 步 |

题库翻 2.5 倍，机器人平均步数只从 2.33 涨到 2.49（+0.16）——
因为新增的 300 人**主要补在原本稀疏的维度上**（左后卫 / 左脚 / 非五大联赛），
分摊后每个属性值的区分度反而更均匀，单次猜测的信息量没有明显下降。
</details>

**怎么读这两个数**：

- 两个模型都是"知道全部 500 人属性 + 能完美过滤"的机器人。真人记不住大部分球员的
  身高和球衣号，实际会明显更慢，**8 次机会是给真人的容错余量**。
- 所以验收盯的是两条硬底线，不是"平均步数要接近 8"：
  1. **最坏步数 ≤ 8** —— 保证不存在"必然猜不出"的死题（当前最坏 4，余量充足）；
  2. **平均步数 ≥ 2** —— 保证有推理过程，不是一步蒙中。
- 看到平均 2 步不必惊慌：这是这类游戏的通病（单次反馈信息量太大），
  Wordle 类产品的理论最优普遍在 3-4 步。想提高真人难度应**扩题库**，
  但按当前每次猜测约缩小 47 倍算，题库要到数万级才能把最优步数推到 5 步 —— 不现实。

## 4.6 本地测试模式（`scripts/test-mock.js`，67 条）

「不开云也能玩」的那套东西没有删掉，而是做成了**可开关**的。两个方向各一个 `.bat`：

```bash
scripts\开启本地测试.bat                # 开启：拼装代码 + 拷 mock 文件 + 自检 + 跑本层回归
scripts\关闭本地测试-提审前必点.bat     # 关闭：拆段 + 删文件 + 跑 check-mp（15 条全绿）
node scripts/toggle-mock.js status      # 只查当前处于哪个模式
```

它由 `scripts/toggle-mock.js` 驱动，**不保存两份整文件**：`_mock-backup/blocks/` 里存的是
10 个带 `MOCK-BEGIN / MOCK-END` 标记的代码片段，`on` 时按锚点插进**当前的正式文件**，
`off` 时只删标记内的内容。**往返任意次结果逐字节一致**（已实测 3 轮 SHA-256 比对）。

这么设计是为了防「副本漂移」：存两份整文件的话，改了正式代码忘了同步副本，
就会被旧代码静默覆盖；拼装则相反 —— 正式代码结构一变，锚点找不到，当场停下来报错。

| 分组 | 关键断言 |
| --- | --- |
| 整局打通 | 开局 → 猜 8 次 → 终局 → 揭晓，返回体与真云函数逐字段一致 |
| ★ SHA-256 对拍 | 12 个用例与 node `crypto` 逐字节一致（含中文与 55/56/57/63/64/65 字节边界） |
| 每日答案 | 同种子同答案；答案池按模式分档（daily 用 `MIN_FAME_DAILY`） |
| 答案守卫 | 未终局时 `gameResult` 拿不到答案（`status === 'playing'` 守卫） |
| api.js 双路路由 | Mock 开启时不调 `wx.cloud`；关闭后两个请求都走云函数 |

> 那 12 条 SHA-256 对拍抓到过本项目最阴的一个 bug（见 §5）：
> 手写的 Σ0 写成了 `ROTR^15`（规范是 **22**），三份独立实现互相一致却都对不上标准库。

**提审前必须关闭**：开着它等于把比对逻辑和 500 人答案池打进客户端。
关掉后 `check-mp.js` 第 7 组的 3 条硬断言会守着这件事（`USE_MOCK === false`、
`miniprogram/utils/` 下无 `mock-*.js`、没有源码还在 `require('mock-*')`）。

## 4.7 线索筛选（`scripts/test-candidates.js`，36 条）

「点线索标签 → 筛出还符合条件的球员」是**唯一一处客户端推理逻辑**，也是最不容易发现错误的地方：一旦它把正确答案筛掉，玩家会看到"明明知道线索却找不到人"，不报错、不崩溃，只是莫名其妙地猜不中。所以它单独成层。

| 分组 | 关键断言 |
| --- | --- |
| 口径对拍 | `TOL` / `POSITION_GROUP` 与 `_shared/constants.js` 一致；`calcAge` 与 `compare.js` 跑 200 人 × 3 个参考日全等；`beijingDateKey` 跨零点/月末/年末与 `util.js` 全等 |

## 4.8 音效（`scripts/test-sfx.js`，24 条）

音效是"错了会直接伤到用户"的东西 —— 音量 0.9、频率 18kHz、3 秒长音都不会报错，但会让人当场静音卸载。而且 `play('拼错的name')` 是**静默失效**的，没有测试根本发现不了。

| 分组 | 关键断言 |
| --- | --- |
| 参数安全区间 | 频率 20~8000Hz；单音 20ms~0.8s；峰值 ≤ 0.3；波形在白名单 |
| 爆音风险 | 按时间轴估算同时发声量（琶音交错，不能简单求和）≤ 0.5 |
| 开关 | `setEnabled` 立即生效；关闭时 `play` 返回 false 且不报错 |
| 非小程序降级 | node 环境（无 `wx`）下 `available()` 为 false、`play` / `unlock` 不抛异常 |
| 调用点静态检查 | 扫描全部小程序源码：20 处 `sfx.play('xxx')` 的名字都在 `TONES` 里（防拼错静默失效）、没有定义了却从不播的音效、用到 sfx 的文件都 require 过 |
| 设置项 | `DEFAULT_SETTINGS.sound = true`；设置页有开关且会同步到 `sfx`、会显示"设备不支持"说明 |
